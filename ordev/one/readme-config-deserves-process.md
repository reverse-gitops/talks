Configuration Deserves a Software Delivery Process Too

Configuration is often some of the most critical logic in a system, yet many teams still manage it with far less discipline than code. It lives in databases, gets edited through admin screens, bypasses proper review, mixes awkwardly with secrets, and moves across environments with limited testing and weak packaging boundaries.

 

That works until configuration becomes important enough to break production.

In this talk I argue that configuration should be treated as a delivery problem, not just a storage problem. Rather than letting users or internal tools edit deployable configuration directly, platforms can capture validated intent through an API and turn it into concrete configuration that is tested, packaged, versioned, signed, and promoted through environments as controlled artifacts.

I will explore where Git still fits, why OCI artifacts provide a useful packaging boundary, and how separating configuration authoring from configuration delivery improves safety, auditability, and rollout control.

 

Attendees will leave with practical ideas for giving configuration a real delivery pipeline, a better understanding of the trade-offs involved, and a clearer sense of why direct configuration mutation is often the wrong default.
